# Interface translation and contributions

**English** | [简体中文](i18n.zh-CN.md)

The CLI, both editors, previews and production statuslines share semantic messages. English is the source and fallback language. Complete documentation is maintained in English and Simplified Chinese; adding an interface language does not require another copy of every document.

This guide describes the I18N-02 [incremental workflow](i18n-workflow.md). English/Simplified Chinese are complete during development; all six official languages must be accepted before public release. See the [implementation and evidence](i18n-02-delivery.md).

## Resource ownership

```text
packages/core/resources/i18n/
  languages.json             Canonical ordered codes and native names
  locales/<code>.json        Canonical UTF-8 message packs
packages/core/src/i18n/       Shared TS messages and generated per-language output
archive/python/src/claude_statusline/i18n/   Frozen Python reference; never regenerated
mods/statusline-native/lib/i18n/
  generated-locales.ts        Generated registry, types and messages; never edit
  index.ts                   Generated copy of the shared pure translator
tools/generation/resources.ts TypeScript resource writer and drift/coverage checks
tools/migration/ts-05/reference.ts Independent historical comparison entry
```

Supported codes, in selector order, are `en`, `zh-CN`, `zh-TW`, `zh-HK`, `ja`, `ko`. Their autonyms are English, 简体中文, 繁體中文（台灣）, 繁體中文（香港）, 日本語, 한국어. Taiwan and Hong Kong have complete independent packs. Selection remains explicit and case-sensitive. The compatibility alias `zh-Hant` resolves to `zh-TW`; it is accepted at CLI, preference, display and import boundaries but is not a seventh selector option. Reads normalize in memory without rewriting files; explicit saves and exports use canonical codes. Other aliases and system-locale detection are unsupported.

A future language requires an explicit maintenance scope and support level in the build-only policy, an acceptance file and its relevant UI/output/search/layout checks. Append its code/name to `languages.json`, add the real `locales/<code>.json`, and validate its metadata before generation. This work adds no language. The registry must match the discovered packs exactly, with English first. New languages require no changes to selectors, CLI choices, protocol enums, search, or installed wizard language lists. Generated files are committed and checked in CI; runtime code never discovers languages by scanning directories.

Raw packs contain real translations. `en`/`zh-CN` (A) must be accepted and complete during development; `zh-TW`/`zh-HK`/`ja`/`ko` (B) may use current English for missing, stale or pending entries. Public release requires complete A/B acceptance. Invalid types, duplicates, unsafe text, new placeholder mismatches and unexplained keys fail. Only unchanged entries with verified old acceptance/contracts can be isolated as history; retired keys do not enter effective resources or coverage denominators. Reports distinguish raw presence, current validity, acceptance and English fallback; none implies native-speaker review. Explicit configuration writes still reject unsupported languages.

Use semantic keys and named placeholders such as `{path}` or `{count}`. All languages must preserve the placeholder set; their order may differ. Positional fields, attribute/index access, formatting specifications and conversions are rejected. Statusline strings must be single-line terminal-safe text, and labels/enum values cannot contain placeholders. Translate complete phrases; preserve commands, IDs, user text and technical units. Do not add runtime translation-service dependencies.


Use the pinned Node 24.21.0 toolchain for generation. Edit canonical raw messages and the build-only lifecycle inputs; core and Mod effective copies are generated together. Acceptance updates use the explicit command below. TS-05 freezes the Python archive and excludes it from generation. Historical comparisons reconstruct the original source layout.

## Incremental authoring

Build-only inputs under `tools/generation/i18n/data/` include `policy.json`, `context.json`, `terminology.json`, per-language `accepted/` records, `history.json`, `provenance.json` and verified baseline snapshots. They ship in the reproducible source archive, not the npm runtime package. Package JSON dictionaries, Node UI dictionaries, Native split modules and statusline modules all use the same effective analysis.

Signatures bind exact English text, named placeholders, contextual meaning and referenced terminology. Bump context meaning/version when English stays unchanged but semantics change. Changed terminology invalidates only referencing keys. Translation edits invalidate their previous hashes. Do not copy English into a raw pack just to satisfy presence. Commands and technical terms may legitimately equal English after validation.

```bash
npm run languages:coverage
npm run languages -- report --format text
npm run languages -- freeze --commit FULL_HEAD_SHA --base FULL_BASE_SHA --output dist/validation/language-freeze.json
npm run languages -- validate --language ja --keys settings.ui-language --review 'Reviewed the immediate-save meaning and terminology in context.' --output dist/validation/language-validation.json
npm run languages -- accept --validation dist/validation/language-validation.json --output dist/validation/language-accepted.json
npm run generate
npm run generate:check
npm run languages -- release-check --format text
```

Use new report paths. `freeze` reads immutable Git inputs without network access or a build/test run; it lists added, changed, parameter-changed, deleted and unfinished entries with English/Chinese reference, placeholders, context, terminology and any declared cell budget. `report`, `freeze`, `validate` and `release-check` never change source or acceptance. `accept` checks the exact current input identity before explicitly updating records/history; source or policy changes require a fresh validation. The contextual review text records work actually performed, not a new reviewer approval. Structural checks alone do not establish linguistic quality. Run the impact-selected product/layout checks as well.

Generation/check requires A readiness and safety for every language. Release-check requires complete A/B readiness, including preview releases; C languages, if later approved, require explicit acceptance/fallback disclosure. Ready PR/main product acceptance can retain safe B fallback without authorizing publication. Complete-source and maintenance-source publication independently verify matching language evidence. Reports never turn missing or expired CI evidence into a passing release.

## Scope and persistence

Interface language covers menus, catalog descriptions, forms, choices, help, progress and recovery messages. `LocalizedText` carries `{key, params, fallback}` with an English-compatible diagnostic fallback; present it in an explicit language at the UI boundary, including nested errors. Keep business decisions on stable codes rather than translated strings. External errors remain raw details.

`statusline-ui.json` remains schema v1. Reads are side-effect-free; corrupt preferences return English and a warning. Explicit writes use locks, backups and atomic replacement; newer schemas remain protected. Switching interface language saves immediately, preserves page/selection/search/input/draft and repaints cell budgets. Failed writes retain the prior language. Other windows read preferences on reopen/reload, without background polling.

Output language is independent, defaults to English and is stored in the display configuration. Its preview changes with the draft; normal Save/Cancel controls persistence. v3.15.0 retains display schema 17 and editor protocol 30; both language types and accepted values derive from the registry, and protocol validation rejects mismatched frontends. Portable v1, runtime v3 and UI preferences v1 remain independent; see the [shared contracts](contracts.md). Claude preferences retain separate Apply. Before downgrading to a package without a selected language, reset both language settings to English and reinstall matching native resources.

## Ranked catalog search

Both editors prepare labels, descriptions and category names for all registered languages, plus IDs and custom labels. Prepared fields retain normalized text and original code-point positions. Queries perform no translation/resource reads; editing a custom label refreshes its own cached field. Interface switches reuse the same multilingual index.

Ranking remains exact, prefix, English word initials, substring, then ordered subsequence, with stable original-order ties. Both implementations apply per-code-point NFKD and lowercase plus collapsed Unicode whitespace. Shared fixtures include Traditional Chinese, kana width/combining marks and Hangul. Matching text is highlighted; alternate-language hits show their original evidence. Generated fallback membership keeps English evidence attributed to English; an accepted technical term identical to English retains its accepted language. Category/query filters retain existing reorder protection, selection and draft behavior.

## Validate a change

Prepare dependencies with the pinned toolchain as described in the [development guide](README.md#development-and-testing). After editing canonical language resources, regenerate and check their owned copies:

```bash
npm run generate
npm run languages:coverage
npm run generate:check
```

Documentation-only changes need only:

```bash
npm run docs:check
git diff --check
```

For committed translation maintenance, use `npm run ci:plan` and its selected `npm run ci:check` tasks with immutable base/head inputs, resolving package comparisons when required; follow [impact checks](impact-checks.md#local-interface). Existing translation values with unchanged keys/placeholders qualify for presentation checks only when generated copies and actual ownership agree. Language registration, keys/placeholders, defaults or product behavior changes require the product route and local `npm run check`. Mixed changes union their checks; unknown ownership or unresolved comparison blocks. Do not run a complete matrix merely because a translation file changed.

Preserve the existing 36 interface/output combinations, forward/backward cycling, save/cancel/reopen, failed writes, import/export and upgrade coverage. Extend the affected existing cases for native 32×12 and external 64×18 minimums, common/resize viewports, long text, Unicode and both background themes. Applicable Native host checks retain independent props, Pane and Client-tree budgets and recovery; follow [capacity rules](native-capacity.md). Run official validation/tests and available exact-host declarations for the affected Mods selected by the plan; the existing 2.1.296 declaration gap remains explicit.

When installed-terminal evidence is required, capture the installed TypeScript npm candidate and record package/source/host/viewport provenance. Automated tests, actual-host mounting, PTYs, agent inspection and physical Windows/macOS terminal acceptance have distinct meanings. Follow [testing](testing.md) and the [release gates](../RELEASING.md), preserving verified [PR/main/tag reuse](ci-maintenance.md#candidate-promotion-across-pr-main-and-tag). These are logical coverage obligations, not a demand to repeat every journey per language or on every promotion. The six accepted [issue #96 gaps](https://github.com/fbincon/claude-code-statusline/issues/96) remain unverified and do not waive new failures.

## Statusline presentation

Only `statusline.*` messages are generated into individual TypeScript language modules. Rendering imports the selected complete effective module on first use; development fallback is already materialized from the current English source. It never parses interface JSON or reads interface preferences. Interface catalog caches cover the registered languages and normalize unknown internal requests before caching.

Pass output language explicitly through production and preview formatters. Translate known enum values at presentation boundaries and keep raw observations, numbers, units, IDs and user labels intact. Owned prefix metadata drives decoration; never recognize labels by matching arbitrary payload text. Keep existing English statusline bytes compatible.

## Regional terminology

Both Traditional packs cover every English key in public releases and retain placeholders, commands, IDs, numbers and technical units. Taiwan uses 介面, 設定, 儲存, 檔案, 資料夾, 軟體, 使用者, 資料, 網路 and 狀態列. Hong Kong uses formal written Chinese with 介面, 設定, 儲存, 檔案, 資料夾, 軟件, 用戶, 數據, 網絡 and 狀態欄. Both use 記憶體, 快取, 欄位, 字串 and 字元 consistently. Key completeness does not establish native-speaker review. Current interfaces follow the persistence section above; language values and the compatibility alias use shared canonicalization.

Native UI translations are generated as one module per language under `mods/statusline-native/lib/i18n/locales`, with a small generated registry. Keep each imported module below the official host limit (1 MiB in current acceptance); generation tests enforce this without dropping messages or languages. The Node UI cache remains aggregated.
