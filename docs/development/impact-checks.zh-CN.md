# 按影响检查与维护证据

[English](impact-checks.md) | **简体中文**

## 分阶段启用

在本地使用影响计划选择常规合并的检查。版本候选走[发布晋升](ci-maintenance.zh-CN.md#候选包在-prmain-与-tag-之间晋级)。

## 职责与检查

分类器读取两个固定 Git 树，包含新增、删除、文件模式和重命名两侧，不依赖 PR 标题、标签或维护者的口头判断。核心行为覆盖 CLI、平台副作用、外部编辑器、Mods，以及 `packages/core`。

| 职责 | 必需检查 |
| --- | --- |
| 维护中的文档和社区模板 | 链接、锚点、双语对应、模板结构和空白错误；已登记现行指南另选择依照源码的内容／示例测试 |
| 文档媒体与 JSON 记录 | 文件引用、媒体封装、PNG CRC／解压／尺寸及可核验的截图摘要 |
| 译文值、帮助文字值字段和已登记主题颜色 | 消息键／占位符、精确资源生成、相关核心／CLI／TUI 测试、适用 Native 宿主测试与打包／安装检查 |
| 测试及共享夹具 | 已登记的消费测试族及适用平台／宿主组合 |
| 检查、工作流、Action 和发布策略 | 工作流身份与检查／发布契约测试，包含失败场景 |
| 基准、验收及开发工具 | 工具测试族和相关系统检查 |
| 构建／生成输入、开发依赖及导出设置 | 实际包内容比较、生成／构建测试和三平台安装 smoke |
| 产品逻辑、协议、运行依赖及内置技能指令 | `npm run check` 加适用的定向诊断 |

模板位置与检查边界见[模板与检查登记表](README.zh-CN.md#模板与检查登记表)。PR 模板结构与任意顶层 Issue 表单路由由 `docs:check` 在本地覆盖；参见[社区文档检查](ci-maintenance.zh-CN.md#社区文档检查)。

文档检查运行于 Linux。纯核心测试默认运行于 Linux；平台、应用、终端和工具测试族保留 Linux、Windows、macOS 执行。Mod 检查使用受影响 Mod 的现有固定宿主清单；不支持 Runtime 的宿主被排除，不报告通过。专项宿主作业执行官方校验／测试和可获得的精确宿主声明检查，不连带执行无关的安装／运行时矩阵。Claude 2.1.296 既有声明缺口继续明确保留。AgentRow 在已固定的 2.1.326 和 2.1.332 上执行，历史计划保留源码提交对应的宿主清单。

仓库的官方 Mod 检查在同一台机器上一次验证一个宿主版本。其余任务等待，从不同 checkout 启动也遵循此规则。轮到该版本后才开始计算文件时限。上一次验证异常中断时，执行器会核对进程归属。若无法确认相关进程已退出，等待超时后会报告原因。若中断的验证来自另一个操作系统账户且其记录不可读，请在该账户的验证进程退出后，用原账户重试。

对于正在运行的版本，默认最多同时执行 4 个测试文件，可用环境变量 `STATUSLINE_MOD_TEST_JOBS` 将上限设为 1 至 8 的整数。每个文件都在独立的插件副本中运行，并保留各自的超时、日志、源码哈希和结果。专项检查启动新文件的窗口为 15 分钟，源码提交中每个测试文件再增加 5 秒。窗口内已启动的文件最多可以运行 180 秒。任务预算另计宿主版本识别、插件校验，以及对应宿主适用的声明和 TypeScript 检查。

多个类别合并检查清单。未知职责、不支持的文件类型、含义不明的文件模式或无法读取的修订均阻断并报告分类问题，不会自动选择昂贵的完整产品矩阵。冻结归档的改动仍须通过归档完整性检查。

产品静态导入关系优先于测试／工具／文档目录标签，包含被内联的编译期输入；这些改动须比较实际包内容。生成夹具始终选择生成检查。workspace 描述性元数据可单独比较，但不忽略入口、依赖或可执行包契约。在本地比较完整 base 和 head，以涵盖同一 PR 的所有提交。

只有保留既有消息键／占位符的译文、已登记帮助文字字面值字段和主题值字段属于展示数据。帮助命令选择器、属性键、控制流、可执行表达式和终端控制字符仍参与比较。语言注册、消息键或默认行为变化仍属于产品改动。生成副本必须与规范源精确一致。产品 `SKILL.md` 属于执行指令，不是普通文档。注释、格式和纯类型改动须证明输出操作等价，并进行实际包内容比较。

依赖分类从四个业务 workspace 追踪运行依赖闭包，包含可选依赖及链接 workspace 的依赖。锁文件中的 `dev` 标记不能单独将运行依赖排除。

制品传输改动属于 CI 策略。本地 Action 及其依赖锁属于验收策略输入。生成轻量 worker 清单的构建工具还需执行包比对。轻量输入须还原完整候选的原包字节、冻结 Node 版本和应有覆盖清单。用专项测试与手工诊断验证传输故障。

## 本地接口

使用固定且已提交的输入。未显式传入 `--compare` 时，规划器只读源码：

```bash
npm run ci:plan -- --base origin/main --head HEAD --output /tmp/impact-plan.json
```

版本化 `ImpactPlan` 记录 base／head／tree 身份、分类器摘要、逐文件原因、选中检查、具体任务及路线：`maintenance`、`product`、`compare` 或 `blocked`。`compare` 表示尚未完成判断，不能生成通过的专项回执。

涉及包内容的改动使用新输出路径完成比较：

```bash
npm run ci:plan -- --base origin/main --head HEAD --compare --output /tmp/impact-compared.json
npm run ci:check -- --plan /tmp/impact-compared.json --task linux \
  --artifact /tmp/impact-compared.json.package/head.tgz --report /tmp/impact-linux.json
```

对计划中与实际平台和宿主匹配的每个任务 ID 运行 `ci:check`。选中 `packaging` 的任务传入 `--artifact`。每个任务使用新的报告路径。CI 验收要求 Actions 执行身份。完整本地 `npm run check` 仍可使用，兼容层验证和核心改动仍要求执行。

包内容比较独立导出两个源码，在禁用生命周期脚本的情况下安装锁定依赖，完成构建、生成校验和打包。内置依赖清单的生命周期脚本参与比较，因为这些脚本会影响 npm 安装。比较运行成员及模式，只允许已登记的文档、编译元数据、版本身份和展示差异。运行表达式、入口、依赖及未登记成员仍参与比较，不改写任何包的提交身份或原始字节。比较错误会阻断规划。运行内容不等价时直接选择产品改动路线。包等价时，规划器再拆分专项维护任务并核对托管作业预算。

## 证据与晋升

本地回执记录已运行任务、实际平台、提交和计划摘要。PR 记录每项结果及适用限制。历史 `ci-maintenance` 及 `ci-release-binding` 仍按归档源码规则读取，含产品基线、制品与原始作业关联。现行发版流程从发版 PR 获取原包并在等价合并和 tag 复用。 [发布指南](../RELEASING.zh-CN.md#绑定源码的-ci-证据晋级)。

## 验证与维护

调度新的专项任务时，规划器按不可变 head 树中的测试文件计算预算，执行前核对编译文件清单。串行测试族启动新文件的窗口为 15 分钟加每文件 5 秒。已开始的文件拥有独立的 15 分钟时限。每个任务都在 360 分钟的托管作业上限内为构建、准备、上传和清理留出时间。

维护路线的规划器会按原有顺序，把超出预算的任务在检查族之间拆分。第一部分沿用任务 ID，后续部分使用编号后缀，例如 `linux-2`。每部分沿用原定的平台和宿主，并为自身的检查出具回执。单独一项检查超出上限时，计划会阻断。调度策略由不可变 head 决定，早期源码仍使用原始任务清单和回执身份。

修改安装验收工具时，除执行计划选中的工具专项外，还要用真实候选验证受影响的场景。涉及模拟执行或 shell 启动时，使用 Windows ARM 宿主上的 x64 进程。对照报告分别记录实际包的 SHA-256 和测试驱动提交。[安装后的语言组合](testing.zh-CN.md#安装后的语言组合)。

回归覆盖真实 PR #181 的 PNG／JSON 变更集、混合维护、产品改动、依赖闭包、重命名、未知文件、跳过／草稿作业、包内容等价、不可变基线执行，以及“完整基线 → 多次维护 → tag/npm”来源链。故障场景包含最新失败运行、过期或损坏产物、错误源码身份及缺失的已选择发布证据。

在作业摘要和交付记录中保留路由决定及原始执行身份，观察实际执行量与耗时；复用回执不是新样本。如需回滚，通过正常评审 PR 回退调度，保留证据读取能力和既有发布身份。另见 [CI 维护](ci-maintenance.zh-CN.md)、[测试](testing.zh-CN.md)及[发布准备](../RELEASING.zh-CN.md)。
