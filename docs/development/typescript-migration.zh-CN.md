## 兼容要求

1. 保留公开 CLI 操作、已记录的参数、环境变量、stdout／stderr 分工与退出行为。`render` 输出文本，`render-subagents` 输出 `id`／`content` NDJSON，编辑器／运行接口返回结构化响应；无效渲染／hook 输入沿用既有静默失败行为。
2. 保留显示实例、ID、布局引用、停用项覆盖、语言和显式关闭偏好。读取、预览、导入审阅和 dry-run 不改写配置。界面语言、输出语言、工具配置与 Claude 偏好继续独立。
3. 对不可信 JSON 保留严格运行时校验，TypeScript 类型不替代输入验证。保留错误码、未知／null／零的区别、数据来源、冲突检测和无关 Claude 设置。
4. 保留原子发布、备份、失败回滚、私有文件处理及加锁事务。在不同实现访问同一可变存储前，确定兼容锁机制或经验证的独占切换流程。
5. 保留任务归属、Stop 候选、续跑、重叠等待、Agent 报告交付、去重、不完整证据及终态冻结。原生单轮耗时不得覆盖任务总耗时。
6. 保留包含睡眠时间、识别重启的计时语义和持久化整数精度。不能先用 JavaScript `number` 读取纳秒字段再转 `bigint`。新增磁盘表示必须具备版本化读取、迁移与恢复测试。
7. 保留固定 Unicode／字符簇宽度、ANSI 重置／背景规则、布局及逐实例格式。重复指标共享原始观测，不增加 transcript／Git 读取或重复累计用量。
8. 保留两个编辑器，以及宿主 Apply 与工具 Save 的独立性。Mod 宿主调用留在受支持入口，共享 Client 代码不得引入 Node 文件／进程依赖。
9. 渲染和被动观测继续使用本地数据。保留现有按需启用及能力门槛；已有 macOS Client 输入限制须有新证据才可变更结论。

仅更换语言不要求 schema 升版。若必须改变语义或表示，应在切换写入方前记录受影响契约、过渡方式、兼容窗口和回滚方案。

## 候选架构

使用统一 TypeScript 业务核心承载配置校验、目录／表单定义、渲染和生命周期规则。文件系统、时钟、进程身份、终端输入输出及宿主 API 使用明确的适配层。CLI 与两个已有 Mod 保持独立入口，仅共享兼容的纯逻辑模块。

首选运行时候选为 Node LTS，并发布编译后的 JavaScript。独立可执行文件属于分发候选，尚未成为既定要求，也不能代替平台验证。具体运行时版本、包管理器、测试框架、终端库、原生依赖和目录布局在 TS-02 后确定；本计划不代表已创建生产工程骨架。

渲染／hook 入口保持轻量，避免提前加载编辑器资源。随子系统迁移，将规范规则转入 TypeScript／共享数据，保留可确定生成的资源与漂移检查。Python 参考实现独立保留用于对照，避免长期维护两套持续演进的规范定义。

- 关闭剩余决策和回归问题，链接最终实现／发布证据，注明最后支持的 Python 版本及过渡方法。

**退出标准：**目标版本已交付，发行物经过验证，限制及恢复方式有据可查。合并重构 PR 或本机可执行文件能运行不代表正式交付完成。

两套实现使用独立的配置／运行样例副本，注入时钟与进程身份，只归一化有说明的非确定字段。新实现不能写入 Python 对照的真实运行目录。每个疑似差异都应判断属于回归还是需要另行记录的既有缺陷，不把缺陷静默固化为新契约。

基线的 [CI](../../.github/workflows/ci.yml) 和 [Native Mod](../../.github/workflows/native.yml) 定义 Linux、Windows、Intel／Apple Silicon macOS 及固定 Claude 宿主覆盖。README 另有 Windows x86／x64 和 WSL 支持说明，必须明确列出未支持或未验证的组合，不假设选定运行时／打包工具天然覆盖。Claude Code 2.1.296 当前有运行／安装覆盖，但现有准备流程未提供声明，不得记作已通过精确版本类型检查。

性能对照使用相同机器、样例、固定源码／脚本版本及明确缓存条件，分别记录运行时启动和完整命令延迟；避免用常驻且已预热的 TS 代码对比新启动的 Python 进程。历史 [v2.0 性能报告](performance-v2.0.0.zh-CN.md)用于选择场景，不是本次迁移的直接测量。不在实测前承诺提速或内存下降。

普通检查使用临时配置且不调用付费模型，尽量复用已捕获生命周期证据。确需新增付费验收时，沿用[测试文档](testing.zh-CN.md)中的既有预算／账本规则，重构不重置账本。Linux CI、模拟时钟和 PTY 捕获不能证明 Windows／macOS 真人交互或真实硬件睡眠／恢复已验收。

## 会话工作流与交接

开始实施会话时，先阅读本计划、相关架构／契约和适用仓库指令；检查工作区及当前 HEAD，识别未完成工作和当前阶段，再选择依赖已满足的下一项有限交付。保留无关修改，沿用既有分支／工作树规则；已有实现正在进行时，不自动启动另一套实现。

每次变更保持可审阅，并包含相关测试；一个阶段可以跨多个 PR。测试提交与合并提交不同时分别记录。若后续稳定修复影响基线，记录新的对照版本并重验受影响案例，历史中保留最初参考提交。

每次交接同步更新中英文的当前状态、阶段表、决策、证据和下一步。原始输出不粘贴进计划；原始捕获使用新的忽略目录，例如 `dist/validation/typescript-migration/<stage>/<run>`，该路径只是拟定组织方式，不代表已有证据。将脱敏且独立可读的结果摘要纳入版本管理，使其他维护者无需本地原始目录也能判断结果；记录环境版本、命令、数量、失败／跳过、提交／脚本／资产摘要及 CI／PR 链接。

阶段开始后使用以下交接记录：

```text
日期与时区：
阶段与状态：
执行者或会话引用：
分支、测试提交、合并提交与 PR：
已完成交付：
检查及结果，包含跳过或未执行项：
变更的决策与剩余风险：
证据摘要与私有原始资料位置：
下一项具体行动：
阻塞原因及解除所需行动，如有：
```

每次更新后检查文档：

```bash
python3 -B tools/check_docs.py
git diff --check
```

规划阶段的文档检查器仍是 Python，在 TS-05 替换此操作说明。已映射行为取得替代证据之前，不删除 Python 对照或宣称全面等价。文档中的后续事项本身不构成开始编码或发布的任务指令。
