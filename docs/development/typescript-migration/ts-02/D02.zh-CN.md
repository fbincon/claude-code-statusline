# D02 — 时钟、进程身份与无损 JSON

[English](D02.md) | **简体中文**

状态: **DECIDED**. 日期: 2026-10-14 (Asia/Shanghai).

证据和阶段状态见 [TS-02](README.zh-CN.md)。

## 方向

通过 Koffi 探测系统时钟及身份 API：Linux 使用 CLOCK_BOOTTIME 与 /proc 启动／进程身份；macOS 使用 mach_continuous_time、kern.bootsessionuuid 和固定语言／时区的 ps；Windows 使用 GetTickCount64、boot GUID 与启动序号组成的版本化身份，以及既有 CreationDate 兼容转换。Windows 身份是下述明确记录的基线修复差异。

## 接口与行为

整数运算使用 bigint，磁盘仍写数字 JSON 字面量。Node 24 JSON.parse reviver 的 context.source 提供原始词元，再构造 LosslessNumber；字段校验先确认整数字面量语法，再转 BigInt。对语法有效 JSON 的键扫描拒绝全部重复键，包括转义同名键和同值重复键；原生 JSON 解析安全保留自有 __proto__ 属性。

## 验证

实测否决了一项行为：lossless-json 4.3.1 的 parse 即使配置 onDuplicateKey 也会忽略同值重复键。保留其数字表示／序列化能力，不把该解析器作为严格入口。保留整数／浮点、缺失／null／零及冻结值的区别。Unicode 键排序与整数哈希与 Python 对照；探针对浮点规范化明确报错，完整浮点 parity 留给 TS-03。

## 替代方案与限制

单独 Date.now 无法提供包含休眠的启动域，单独 hrtime 不能确立跨进程／重启持久化语义。不能从可调整的墙钟推导启动身份。不可用身份保持不可用，计时退回降级证据，不虚构精度。本实验不改变磁盘 schema。

## 恢复及出口

原生 CI 证明 API 绑定和 Python 一致性，注入观察值证明失败路径。
2026-10-12 的[本机物理补验](validation.windows-local-20261012.json)中，Windows 11 x64
约 60.48 秒 S0 现代待机／恢复通过，但**真实重启的身份验收失败**：系统启动事件和
启动时钟从 2059.515 秒降至 160.312 秒确认已重启，Node 与固定 Python 参考的 boot GUID
却保持不变。独立 ctypes 的 `NtQuerySystemInformation(90)` 返回成功、32 字节结果及同一 GUID。

重放这组真实样本时，两种未修改实现均返回不可用的 elapsed delta；参考一致性不能代替
跨重启身份正确性。原始快照、系统事件、失败核验及独立诊断均保留。该轮原方案诊断未确立
系统返回值保持不变的原因或替代身份方案；后续修复及复验见下节，不移动 TS-01 参考来消除失败。
本机失败修复时 D02 仍为 OPEN；最终处置见下方 2026-10-14 决策闭合。S0 结果不代表 S3 或休眠验收。

Windows CI 还证明：句柄保留进程对象时，退出后仍可能读取创建 token。因此启动器原型单独检查存活状态（Windows 使用零等待进程查询），不把参考 token 重新解释为存活证明。

## Windows 启动身份 v2 修复

维护者在本机失败复现后明确要求修复。Python 当前源码及 TS 候选现在生成
`windows:v2:<GUID>:<BootId>`；[微软文档](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/ntddk/ns-ntddk-kuser_shared_data)
将 `KUSER_SHARED_DATA.BootId` 定义为 OS loader 每次启动递增的序号。
通过 `ReadProcessMemory(GetCurrentProcess(), ...)` 读取当前进程共享页的 4 字节字段，
验证读取长度和非零值；失败时身份保持不可用，不回退到有歧义的 GUID，也不从墙钟推算身份。
读取位置采用 WDK 的用户共享页地址 `0x7ffe0000` 和 `BootId` 偏移 `0x2c4`，
不同架构与版本的支持仍受实际平台证据约束。

兼容差异限定为 Windows 的新启动身份，以及旧 `windows:<GUID>` 样本的降级处理：
旧身份不再具有可信 uptime 域，elapsed 回退到非负墙钟差，可信执行时间标为降级；
同一 v2 启动域仍优先使用包含睡眠的 uptime，不受墙钟校时影响。
已冻结的整数值、磁盘 schema 和进程 token 语义保持不变。

TS-01 的 `9b6d2fa` 参考、固定样例和旧失败记录均不改写。
`current-clock.py` 显式对照修复后的 Python 源码；原 oracle 仍单独验证原时钟／进程 token，
Windows 的身份差异有专门断言。收据同时绑定 Python 时钟、平台环境、进程适配及计时源码哈希。
[修复验证记录](validation.windows-boot-fix-20261012.json)区分原失败、自动回归和新的物理复验。
修复版已通过本机约 112.70 秒 S0 待机／恢复，Python 与 Node 的启动序号均保持 1301，
包含睡眠的 elapsed 计算及可信启动域检查通过。随后在 2026-10-12 11:40（Asia/Shanghai）
真实重启，两种实现的启动序号均从 **1301 变为 1302**；系统启动事件、源码／运行时哈希、
新启动身份及跨重启墙钟回退检查全部通过，执行时间信任标志为 false，符合降级约定。
本机 Windows 阻断问题已验证修复；其他架构／系统的修复后矩阵和物理门槛仍须分别处理，
该 Windows 单项结果没有独自关闭 D02 或 TS-02，最终整合处置另述。

[物理检查工具](../../../../tools/windows_clock_smoke.py)接受固定 Node 的绝对路径，
在全新目录分别执行 `before --kind suspend` 或 `before --kind reboot`，真实操作后执行
`after --human-confirmed`。工具核对源码／运行时哈希、Python／Node 身份、内核电源事件和
降级语义；它不触发电源操作。没有实际电源事件的对照运行必须失败。

## 2026-10-14 决策闭合

采用 Koffi 原生适配、bigint 与严格无损 JSON 边界。Windows v2 实体机睡眠／重启、macOS 虚拟机重启、本 Linux 实体机 s2idle／重启均有独立证据；修复后的八目标 CI 已通过。Linux 两次电源操作均验证源码／运行时一致、启动身份及计时可信性；不将 macOS 虚拟机未生效的 Sleep 算为通过。实体 macOS 睡眠等外部缺项按维护者批准保留到发布前。

见 [Linux 整合、CI 与发布前补验清单](LINUX-20261014.zh-CN.md) 和
[原始回执摘要](validation.linux-local-20261014.json)。该阶段决定不代替完整迁移验收；恢复仍按上述保留的 Python 安装／兼容备份处理。
