# D02 — Clocks, process identity and lossless JSON

**English** | [简体中文](D02.zh-CN.md)

State: **DECIDED**. Date: 2026-10-14 (Asia/Shanghai).

Evidence and stage status: [TS-02](README.md).

## Direction

Probe operating-system clock and identity APIs through Koffi. Linux uses CLOCK_BOOTTIME and /proc boot/start identities; macOS uses mach_continuous_time, kern.bootsessionuuid and locale/timezone-fixed ps; Windows uses GetTickCount64, a versioned identity combining the boot GUID and boot sequence, and the existing CreationDate-compatible token conversion. Windows identity is the explicitly recorded baseline correction below.

## Interface and behavior

Use bigint for integer arithmetic and retain numeric JSON literals on disk. Node 24 JSON.parse reviver context.source captures the original lexeme before constructing LosslessNumber; field validators explicitly require integer syntax before BigInt conversion. A key scanner over syntactically valid JSON rejects every duplicate, including escaped and equal-value duplicates. Native JSON parsing preserves own __proto__ keys safely.

## Validation

An important rejected behavior: lossless-json 4.3.1 parse suppresses equal duplicates even with onDuplicateKey. Its numeric representation/serializer remain usable; its parser is not the strict entry point. Preserve integer-versus-float, missing/null/zero and frozen values. Canonical Unicode-key sorting and integer hashes are compared with Python; float canonicalization explicitly fails in this probe and remains TS-03 parity work.

## Alternatives and limitations

Date.now alone cannot supply a suspend-aware boot domain; hrtime alone does not establish persistent cross-process/reboot semantics. Do not derive boot identity from adjustable wall time. Unavailable identities stay unavailable and timing falls back with degraded evidence, never invented precision. No disk schema bump is made by this experiment.

## Recovery and exit

Native CI establishes API binding and Python equivalence, while injected observations establish failure paths.
The [2026-10-12 physical follow-up](validation.windows-local-20261012.json) passes
about 60.48 seconds of S0 Modern Standby/resume on Windows 11 x64, but **real reboot
identity acceptance fails**. OS startup events and uptime falling from 2059.515
to 160.312 seconds establish a restart, while Node and the fixed Python reference
retain the same boot GUID. An independent ctypes `NtQuerySystemInformation(90)`
call succeeds, returns 32 bytes and produces the same GUID.

Both unchanged implementations return an unavailable elapsed delta when replaying
this physical sample pair. Reference equivalence cannot substitute for correct
cross-reboot identity. Raw snapshots, OS events, failed verification and independent
diagnostics are retained. That original diagnostic run established neither the cause
of the stable OS return value nor a replacement identity scheme. The correction and
revalidation below preserve the TS-01 oracle. The local failure is now fixed, while
D02 remained OPEN at that checkpoint; final disposition is recorded below. S0 does not establish S3/hibernation acceptance.

Windows CI also showed that a creation token can remain readable after exit while handles retain the process object. The launcher prototype therefore checks liveness separately (a zero-time process wait on Windows); it does not reinterpret the reference token as proof of life.

## Windows boot identity v2 correction

The maintainer explicitly requested a fix after the local reproduction. Current
Python sources and the TS candidate now generate `windows:v2:<GUID>:<BootId>`.
[Microsoft documents](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/ntddk/ns-ntddk-kuser_shared_data)
`KUSER_SHARED_DATA.BootId` as the sequence incremented by the OS loader for each
boot attempt. `ReadProcessMemory(GetCurrentProcess(), ...)` reads the four-byte
field from the current process's shared page, checking the byte count and a
nonzero value. Failure leaves identity unavailable; neither the ambiguous GUID
nor an identity derived from wall time is used as a fallback. The read uses the
WDK user shared-page address `0x7ffe0000` and BootId offset `0x2c4`; architecture
and version coverage still depend on actual platform evidence.

The intentional differences are limited to the new Windows identity and handling
of legacy `windows:<GUID>` samples. Legacy identities no longer establish trusted
uptime: elapsed falls back to a nonnegative wall-clock difference, with execution
precision degraded. The same v2 boot domain still uses suspend-inclusive uptime
through wall-clock adjustments. Frozen integer values, disk schema and process
token semantics remain unchanged.

The TS-01 `9b6d2fa` oracle, fixed cases and earlier failure receipts are unchanged.
`current-clock.py` explicitly compares the corrected Python sources. The original
oracle separately checks the original clocks/process token, with an explicit
Windows identity-deviation assertion. Receipts also bind Python clock, platform
environment, process-adapter and timing source hashes. The [fix validation record](validation.windows-boot-fix-20261012.json)
separates the original failure, automated regressions and new physical validation.
The corrected implementation passes about 112.70 seconds of local S0 standby/resume:
Python and Node both retain boot sequence 1301, include sleep in elapsed time,
and preserve trusted same-boot coverage. A subsequent real reboot at 11:40 on
2026-10-12 (Asia/Shanghai) changes both implementations' sequence from **1301 to
1302**. OS startup events, source/runtime hashes, new boot identity and cross-boot
wall-clock fallback all pass. Execution-time trust is false, as required for
degraded evidence. This Windows blocker is verified fixed locally; the updated
matrix and physical gates for other architectures/systems still need separate
disposition; this Windows result alone did not close D02 or TS-02. Final integration is recorded below.

The [physical-check tool](../../../../tools/windows_clock_smoke.py) takes an absolute
pinned Node path. Use a fresh directory for `before --kind suspend` or
`before --kind reboot`, then run `after --human-confirmed` following the real
action. It checks source/runtime hashes, Python/Node identities, kernel power
events and degradation semantics; it never initiates a power action. A control
run without a real power event must fail.

## Decision closure, 2026-10-14

Select Koffi native adapters, bigint and the strict lossless JSON boundary. Windows v2 physical sleep/reboot, macOS guest reboot and this physical Linux s2idle/reboot have independent evidence; the repaired eight-target CI passes. Both Linux power actions validate unchanged source/runtime bytes, boot identity and timing trust. The ineffective macOS guest Sleep attempt is not a pass; physical macOS sleep and remaining external gaps stay required before release by explicit maintainer disposition.

[receipt summary](validation.linux-local-20261014.json). This stage decision does
not establish full migration acceptance; recovery retains the Python installation
and compatible backups described above.
