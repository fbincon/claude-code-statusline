# D03 — Compatible locking and publication

**English** | [简体中文](D03.zh-CN.md)

State: **DECIDED**. Date: 2026-10-12 (Asia/Shanghai).

Evidence and stage status: [TS-02](README.md).

## Direction

Prefer the existing lock namespace: flock on POSIX and LockFileEx on the first byte on Windows, including an empty lock file. The Windows native handle is closed to release the lock. Independent Python/TS writers, both holder/waiter directions and killed holders must pass on each native target.

## Interface and behavior

Publish through a private same-directory temporary file, flush file data, replace atomically, then sync the parent directory on POSIX. Only the existing unsupported-directory-sync errors on macOS are soft failures. Windows retries sharing/access failures on the frozen 10/20/40/80/160 ms schedule; permanent errors preserve the old target.

## Validation

Tests cover 16 competing mixed writers, Python-first and TS-first death/release, injected publication failure, kills before/after replacement, POSIX permissions, symlinks/reparse points, and real Windows sharing denial. Crash tests accept only complete old/new bytes. Abrupt death may leave a private orphan; the harness removes only files from its own isolated run.

## Alternatives and limitations

Reject a mkdir-only lock as a silent replacement: old Python writers do not participate. Keep backup/recovery under the same store lock. This is not an NFS/SMB, power-loss or race-resistant sandbox guarantee. General production transactions and orphan ownership/recovery policy remain TS-03/TS-04 work.

## Recovery and exit

The eight-target native matrix at `f891065` passed, including Windows/Python mutual exclusion, so this primitive and strategy decision is accepted. Full production store transactions and installed upgrade acceptance remain in TS-03/TS-04; this does not enable live TS writers. Reopen D03 and isolate writers if later target validation disproves lock interoperability.
